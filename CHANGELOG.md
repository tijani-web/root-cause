## Iteration 1: Synthetic Dataset & Deterministic Signatures
**What changed:** Built a generator (`cmd/generate/main.go`) that produces 13 synthetic performance scenarios using an OpenTelemetry-inspired JSON schema. Each scenario injects one specific bottleneck (e.g., N+1 queries, lock contention) plus red-herring noise metrics designed to mislead a naive LLM. Built a deterministic Go Verifier (`internal/signatures/signatures.go`) with delta-based signature checks against a healthy baseline.

**Evidence that guided the decision:** Initial experiments with absolute thresholds (e.g., "latency > 500ms = problem") failed across different synthetic loads. Switched to relative baselining (e.g., "lock_wait_p95 must exceed 5x the healthy baseline") which is environment-independent. Validated with `go run cmd/verify/main.go` — all 13 scenarios pass deterministically.

---

## Iteration 2: Baseline LLM Evaluation
**What changed:** Implemented a single-shot LLM call (the "Baseline") that receives only the incident snapshot and produces a diagnosis via Tool Use.

**Evidence that guided the decision:** The Baseline scored 6/13 (46%). It consistently hallucinated causes based on injected red-herring noise. For example, in Scenario 01 (N+1 Query), the Baseline blamed `slow_downstream` because external call latency was slightly elevated as noise. In Scenario 12 (Clean), the Baseline hallucinated a bottleneck when none existed. This proved the necessity of an active validation loop.

---

## Iteration 3: Detective/Verifier Rejection Loop
**What changed:** Implemented the two-stage agentic architecture. The LLM's hypothesis is now verified by the Go Verifier. If rejected, the LLM receives the exact failing condition (e.g., "lock_wait_p95_ms not > 5x baseline") and is forced to reconsider. The loop runs up to 4 attempts.

**Evidence that guided the decision:** The Agent immediately jumped to 11/13 correct. The trajectory logs (`data/trajectories/`) show the self-correction in action: Scenario 07 (Thread Starvation) took 3 attempts with 2 rejected hypotheses before converging on the correct cause.

---

## Iteration 4: Strict Schema via Anthropic Tool Use
**What changed:** Replaced prompt-based JSON parsing with native Anthropic Tool Use (`tool_choice: {type: "tool", name: "submit_diagnosis"}`). The schema enforces `proposed_cause` (enum), `confidence` (0–1), `evidence` (array of metric deltas), `ruled_out` (array of rejected alternatives), and `reasoning`.

**Evidence that guided the decision:** Before Tool Use, the LLM occasionally wrapped its JSON in markdown fences or added preamble text, causing parsing failures. Tool Use eliminated 100% of JSON parsing errors. The Agent held at 12/13.

---

## Iteration 5: Dominant-Cause Resolution & Composite Signatures
**What changed:** Replaced the stub signal-strength scorer with a real normalized overshoot function (`internal/signatures/scorer.go`). When the LLM's hypothesis passes verification, the Verifier now also scores all other passing signatures. If a stronger signal exists, the LLM's pick is rejected. Added a composite `lock_and_downstream` signature that fires only when both `lock_contention` and `slow_downstream` pass simultaneously.

**Evidence that guided the decision:** In the previous iteration, Scenario 13 (Lock + Downstream overlap) was the sole failure. The agent could not distinguish between two simultaneously passing signatures. The composite signature and dominant-cause scorer give the Verifier the ability to recognize multi-signal incidents and redirect the LLM toward the correct composite label.

---

## Main Failure Mode
Scenario 13 (Lock Contention AND Slow Downstream) was the hardest case because multiple bottleneck signatures overlap. The agent recognized a problem but could not untangle the compounding metrics using only single-cause reasoning. This was addressed in Iteration 5 by adding composite signatures. The fundamental limitation remains: if two causes have nearly identical signal strength and no composite signature exists, the system will accept whichever the LLM proposes first.

## The Hot Take
During development, we discovered that LLMs in observability contexts are chronic people-pleasers. Given a clean, healthy dashboard (Scenario 12), the Baseline hallucinated a bottleneck anyway rather than admitting nothing was wrong.

The most valuable thing the Verifier loop provides is not catching incorrect diagnoses — it is giving the agent mathematical permission to safely report "No Confirmed Cause" without hallucinating. That restraint is the single most important capability for a production-grade diagnostic agent, and it is the core reason the Detective/Verifier architecture outperforms single-shot analysis by 46 percentage points.
